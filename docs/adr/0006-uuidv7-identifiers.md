# 0006. UUIDv7 for every identifier

- Date: 2026-09-23
- Status: accepted
- Deciders: lead agent, maintainer

## Context and problem statement

Mobile clients in the field often have no connectivity. A reporter must be able to create a
report offline, attach photos, and sync later, possibly several times if the network drops
mid-request. The server must recognise a resubmitted report as the same report rather than
a duplicate. Identifiers also appear in the open dataset, in exports and in citations by
researchers, so they must be stable, globally unique and must not leak counts or allow
enumeration.

What identifier scheme should every entity use, and who generates identifiers?

## Decision drivers

- Offline mobile clients: identifiers must be generatable on the device, before sync.
- Idempotent create: a retried `PUT`/`POST` with the same id must not create a duplicate
  (together with `Idempotency-Key`, [0003](0003-fastapi-with-app-factory.md)).
- Index locality: inserts into B-tree primary keys should not scatter randomly.
- Research consumers and provenance: stable, globally unique ids safe to publish and merge
  across datasets.
- Privacy: ids must not reveal row counts or allow guessing neighbouring records.
- Deterministic tests: ids come from an injected `IdGenerator` (`AGENTS.md` §4.2).

## Considered options

1. UUIDv7 (RFC 9562) everywhere (chosen)
2. Serial / identity integers
3. UUIDv4
4. ULID
5. Snowflake-style 64-bit ids

## Decision outcome

Chosen option: **UUIDv7 for every identifier**, stored in PostgreSQL's native `uuid` type,
because it can be generated anywhere, is standardised, and is time-ordered for index
locality.

- Report ids are generated by the client, so an offline-created report keeps its id through
  every sync attempt; a repeated create with the same id and payload is idempotent, and
  with a different payload is a conflict. The server validates that client ids are
  well-formed UUIDv7 values.
- All other ids are generated server-side.
- Generation goes through an `IdGenerator` port in `shared_kernel`, injected wherever ids
  are created, so tests use a deterministic Fake.
- Python 3.14 ships `uuid.uuid7()`; Python 3.13, our minimum, does not. The production
  adapter therefore uses either a small third-party library or an in-house RFC 9562
  implementation behind the port, and can switch to the standard library once 3.13 support
  ends. **That library-or-in-house choice is deferred to Phase 1**, where the first entity
  needs it.

### Consequences

- Good, because offline clients can create and reference records (for example attach
  photos to a report) before the server has seen them.
- Good, because time-ordered ids keep primary-key indexes compact and inserts append-mostly.
- Good, because ids are safe to publish, merge across datasets and cite.
- Good, because the port keeps generation replaceable and tests deterministic.
- Bad, because UUIDv7 embeds a millisecond creation timestamp, so an id reveals roughly
  when it was created; for reports this is usually already public, but it must be kept in
  mind for any record whose creation time is sensitive.
- Bad, because client-generated ids can be malformed, forged with a misleading timestamp, or
  collide deliberately; the server must validate format, never trust the embedded
  timestamp as the report time (reported and observed times are separate fields), and
  treat an id clash with a different payload as a conflict.
- Bad, because 128-bit ids are larger than integers in every index and foreign key, and are
  less friendly for humans reading them aloud; a short human-facing reference may be
  needed later for moderators and callers.
- Bad, because until Python 3.13 support is dropped we carry a library or our own
  implementation.

## Pros and cons of the options

### UUIDv7

- Good, because it is an RFC standard, globally unique, client-generatable and time-ordered.
- Bad, because it exposes creation time and is 16 bytes.

### Serial integers

- Good, because they are small, fast and human-friendly.
- Bad, because they cannot be generated offline, which breaks idempotent offline sync.
- Bad, because they leak counts and invite enumeration of public resources.

### UUIDv4

- Good, because it is universal and reveals nothing.
- Bad, because random ids scatter B-tree inserts and hurt index locality as tables grow.

### ULID

- Good, because it is time-ordered and has a compact text form.
- Bad, because it is not an IETF standard, and PostgreSQL and most tools have no native
  type for it; UUIDv7 gives the same ordering in the standard `uuid` type.

### Snowflake-style ids

- Good, because 64-bit ids are compact and ordered.
- Bad, because they need coordinated worker ids, which offline mobile devices cannot have.

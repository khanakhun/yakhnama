# Data dictionary: audit

The `audit` module keeps the append-only audit log: one `AuditEntry` for every domain
event, written by an outbox subscriber after the change commits. It was introduced in
Phase 3. Column conventions are in [README.md](README.md). **Proposed** marks a
default the maintainer has not confirmed yet. The open questions at the end of this
page list each one.

Source code: `src/yakhnama/modules/audit/domain/`.

## Principles

- **Append-only.** An entry is written once and never changed or deleted. The domain
  model is frozen and has no state-changing methods. Anything that tries to change an
  entry is a defect and raises `AuditEntryImmutableError`.
- **Ids, codes and digests only.** An entry never copies free text from the event it
  records: not a description, a citation, a reason or a name. The event's whole
  content is reduced to `payload_digest`, a SHA-256 digest. Anyone who holds the
  event can recompute the digest and prove what it said, but the audit log itself
  reveals nothing more than ids and codes.
- **The audit log emits no events.** It records the events of every other module.
  An event per entry would feed the subscriber that writes entries and recurse.

## AuditEntry (entity)

| field | type | unit | meaning | provenance | since |
|-------|------|------|---------|------------|-------|
| `id` | `UUID` (v7) | — | Stable identity of the entry. | Generated by the platform's `IdGenerator` when the entry is written. | Phase 3 |
| `occurred_at` | `datetime` (UTC) | — | When the recorded change happened. It is the event's `occurred_at`, not the time the subscriber ran, so a delayed relay does not move history. It is a system timestamp, so it has no `DatePrecision`. | The recorded event. | Phase 3 |
| `actor_id` | `UUID` (v7), nullable | — | The user who caused the change. It is `null` for the system. | The authenticated actor of the causing request. | Phase 3 |
| `actor_kind` | `user` \| `system` | — | Who acted. It is `user` exactly when `actor_id` is set (**proposed**, Q-A3). | Derived from `actor_id`. | Phase 3 |
| `action` | `str` (2–64, `^[a-z][a-z0-9_.]{1,63}$`) | — | What happened: the event's `event_type`, for example `reports.report_submitted`. | The recorded event. | Phase 3 |
| `target.target_type` | `str` (1–64, snake case) | — | The type of the aggregate the change was about, for example `source`. | The event's `aggregate_type`. | Phase 3 |
| `target.target_id` | `UUID` (v7) | — | The id of that aggregate. | The event's `aggregate_id`. | Phase 3 |
| `before_digest` | `Digest`, nullable | — | Digest of the aggregate's state before the change, when the writer has it. A creation has none. | Computed with `compute_state_digest` by the writer. | Phase 3 |
| `after_digest` | `Digest`, nullable | — | Digest of the aggregate's state after the change, when the writer has it. | Computed with `compute_state_digest` by the writer. | Phase 3 |
| `request_id` | `str` (1–128, safe text), nullable | — | Correlation id of the HTTP request or background task that caused the change. It is generated by the platform or sent by a client as `X-Request-ID`; it is never typed by a person. | The platform's request context. | Phase 3 |
| `event_id` | `UUID` (v7) | — | Id of the recorded domain event. It is meant to be unique among entries, so a redelivered event is recorded once (enforced by persistence). | The recorded event. | Phase 3 |
| `payload_digest` | `Digest` | — | SHA-256 digest of the event's canonical JSON (see below). | Computed by `from_domain_event`. | Phase 3 |

## Digest

`sha256:` followed by 64 lower-case hexadecimal digits, for example
`sha256:9f86d0…`. Lower case only, so a digest has exactly one spelling. The prefix
names the algorithm, so it can change later without ambiguity.

## Canonical JSON

`payload_digest` is the digest of the event's canonical JSON, so the same event gives
the same digest in every process and on every Python version:

- the event is dumped by Pydantic, with its `event_type` added; UUIDs and datetimes
  become strings, and UTC is written `Z`;
- object keys are sorted, and there is no insignificant whitespace;
- sets are sorted by their canonical encoding, because a set's iteration order
  depends on the process's hash seed; lists and tuples keep their order;
- non-ASCII characters are escaped as `\uXXXX`.

Changing any of these rules changes every digest, so it needs an ADR.

## Errors

| error | family | raised when |
|-------|--------|-------------|
| `AuditEntryNotFoundError` | `not_found` | No entry has the requested id. |
| `AuditEntryImmutableError` | `invariant_violation` | Any code path tries to change or delete an entry. Kept for the application and persistence layers. |

## Events

None. See [Principles](#principles).

## Open questions raised by this module

| # | Question | Proposed default | Blocking |
|---|----------|------------------|----------|
| Q-A1 | How long are audit entries kept, and may they ever be deleted, for example after a legal request about a user? | Kept indefinitely. They hold ids and digests only, so a user's erasure removes the user record, and the entries keep only an id that no longer resolves. | no (privacy-relevant) |
| Q-A2 | Who may read the audit log? | Admins only, never public. To be decided in the application and API phases. | no |
| Q-A3 | Is every actor either a user with an id or the system without one? Are there service accounts or organisations acting as actors? | Only `user` and `system`. | no |
| Q-A4 | `action` allows 64 characters and `target_type` 64, but an event's `event_type` allows 100 and `aggregate_type` 100. An event beyond 64 cannot be audited. Should the limits match? | Keep 64 in audit and keep event types short. The outbox subscriber fails loudly on a longer one rather than truncating it. | no |
| Q-A5 | Should the entry also record when it was written (`recorded_at`), separate from `occurred_at`? | Not in the domain. Persistence may add a database default column. | no |

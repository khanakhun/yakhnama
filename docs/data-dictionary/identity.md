# Data dictionary: identity

The `identity` module mirrors users from the OpenID Connect provider, and holds
organisations, memberships, platform roles and the authorisation policies every other
module uses. It was introduced in Phase 2. Column conventions are in
[README.md](README.md). **Proposed** marks a default the maintainer has not confirmed
yet. The open questions at the end of this page list each one.

Source code: `src/yakhnama/modules/identity/domain/`.

## Personal data

Yakhnama never stores passwords, because authentication is OIDC-only (ADR 0005). The
identity module stores **no personal data beyond an optional display name**. In
particular it never stores:

- email addresses;
- phone numbers;
- legal, given or family names, beyond the optional display name the user chooses;
- addresses, dates of birth or any other profile attribute from the token,
  including its `name` and `preferred_username` claims: the display name comes only
  from the user, through `PATCH /me`.

If a contact channel is ever needed, that is an open question for the maintainer
(Phase 2 plan, T3). No field is added for it in advance. The display name, the OIDC
subject and issuer, and suspension reasons are never copied into domain events, error
messages or logs.

## User (aggregate root)

A mirror of one person's identity at the OIDC provider. It is created the first time a
valid token for that `(issuer, subject)` pair is seen. It is never deleted.

| field | type | unit | meaning | provenance | since |
|-------|------|------|---------|------------|-------|
| `id` | `UUID` (v7) | — | Stable identity of the user in Yakhnama. | Generated by the platform's `IdGenerator` at first sight. | Phase 2 |
| `subject` | `str` (1–255, printable ASCII) | — | The OIDC `sub` claim: an opaque, case-sensitive identifier that the issuer never reassigns. It is stored verbatim, with no trimming or case-folding. Together with `issuer` it is unique among users and never changes. | The validated access token's `sub` claim. | Phase 2 |
| `issuer` | `str` (1–512) | — | The OIDC `iss` claim. It must be an `https` URL with a host and no user information, query or fragment. Plain `http` is accepted only for loopback hosts (`localhost`, `127.0.0.0/8`, `::1`), so that the development realm works (**proposed**, Q-I6). It is compared exactly. | The validated access token's `iss` claim. | Phase 2 |
| `display_name` | `str` (1–120), nullable | — | The name the user wants shown. It is normalised to Unicode NFC and stripped, and it may not contain the characters listed in [Text rules](#text-rules). This is the only personal data stored. It is optional and the user can edit it. A new user starts with none: the token's name claim is never copied, so no personal data comes from the provider unless the user chooses it. | The user, through `PATCH /me`. | Phase 2 |
| `roles` | set of `Role` | — | Platform roles the user holds explicitly. Implied roles are not stored (see the `Role` table). An active user always holds `citizen`. | Realm roles copied from the token at first sight, plus roles granted by an admin in Yakhnama (Q-I1). | Phase 2 |
| `status` | `active` \| `suspended` | — | Lifecycle state. A suspended user keeps their roles, but no actor is built for them, so no policy allows them anything. | Admin decision. | Phase 2 |
| `status_reason` | `str` (1–500), nullable | — | Why the user was suspended. It is set exactly when `status` is `suspended`. It is free text written by a moderator or admin, so it stays on the record and is never copied into events. | Admin. | Phase 2 |
| `version` | `int` (1 to 2 147 483 647) | count | Optimistic-concurrency version. It is 1 at creation and goes up by 1 with every change that has an effect. `last_seen_at` updates do not change it. | Computed by the aggregate. | Phase 2 |
| `created_at` | `datetime` (UTC) | — | When the user was first seen. This is a system timestamp, so it has no `DatePrecision`. | Platform `Clock`. | Phase 2 |
| `updated_at` | `datetime` (UTC) | — | When the user last changed. It is never earlier than `created_at`. `last_seen_at` updates do not move it. | Platform `Clock`. | Phase 2 |
| `last_seen_at` | `datetime` (UTC) | — | When the user last made an authenticated request. It never moves backwards and is never earlier than `created_at`. It is updated without a version bump or an event, so that routine requests do not change the user's `ETag`. | Platform `Clock`. | Phase 2 |

## Role

A platform-wide role. Implication is a **proposed** partial order (Q-I2): holding a role
also grants every role it implies. Implication is reflexive and transitive, and no two
different roles imply each other.

| value | meaning | implies | status |
|-------|---------|---------|--------|
| `citizen` | Any signed-in person. Every active user holds it. It cannot be revoked; suspension is how a user loses the right to act. | — | plan |
| `trusted_reporter` | A reporter whose reports get lighter triage (Phase 3). | — | plan |
| `org_member` | Realm-level marker that the user belongs to an organisation. Rights inside an organisation come only from a `Membership`, never from this role (**proposed**, Q-I3). | — | plan |
| `org_admin` | Realm-level marker that the user administers an organisation. The same caveat as `org_member` applies. | `org_member` | plan |
| `moderator` | Verifies reports into events and moderates content. | — | plan |
| `admin` | Platform administrator. Manages reference data, roles and organisations. | `moderator` | plan |

## Organization (aggregate root)

A group whose members report and work together, such as a government department, NGO,
research group, media outlet or community organisation. It is never deleted.

| field | type | unit | meaning | provenance | since |
|-------|------|------|---------|------------|-------|
| `id` | `UUID` (v7) | — | Stable identity of the organisation. | Platform `IdGenerator`. | Phase 2 |
| `slug` | `str` (2–64) | — | URL-safe handle: lower-case ASCII letters, digits and `-`, starting with a letter or digit, so it can hold none of the characters listed in [Text rules](#text-rules). It is unique among organisations. | The user who creates the organisation. | Phase 2 |
| `name` | `str` (1–200) | — | Display name. It is normalised to NFC and stripped, and it may not contain the characters listed in [Text rules](#text-rules). It is not copied into events. | Creator, then organisation admins. | Phase 2 |
| `organization_type` | `OrganizationType` | — | The kind of organisation: `government`, `ngo`, `research`, `media`, `community` or `other` (**proposed** list, Q-I4). | Creator. | Phase 2 |
| `status` | `active` \| `suspended` \| `retired` | — | Lifecycle state. `active` and `suspended` can be switched both ways. Either can move to `retired`, which is final. Only an active organisation can be renamed or gain members. | Admin decision. | Phase 2 |
| `status_reason` | `str` (1–500), nullable | — | Why it was suspended or retired. It is set exactly when `status` is not `active`, and it is never copied into events. | Admin. | Phase 2 |
| `version` | `int` (1 to 2 147 483 647) | count | Optimistic-concurrency version. It is 1 at creation and +1 per change. | Computed by the aggregate. | Phase 2 |
| `created_at` | `datetime` (UTC) | — | When the organisation was created. | Platform `Clock`. | Phase 2 |
| `updated_at` | `datetime` (UTC) | — | When it last changed. It is never earlier than `created_at`. | Platform `Clock`. | Phase 2 |

## Text rules

Display names, organisation names and status reasons are normalised to NFC and
stripped. After that they must not contain:

- control characters (Unicode category `Cc`, NUL included), which are unsafe in
  logs and exports;
- lone surrogates (category `Cs`), which cannot be encoded as UTF-8 and would fail
  only when the record is serialised;
- bidirectional embedding, override and isolate characters (U+202A–U+202E,
  U+2066–U+2069), which make text display differently from how it is stored and
  compared ("Trojan Source", CVE-2021-42574).

Slugs are ASCII-only, so none of these can appear in them. Error messages are
fixed strings that never repeat an input value; ids, slugs and statuses appear only
in the error's `details`.

## Membership (entity)

One user's membership of one organisation. A user has at most one membership per
organisation. Only a platform admin may add a member for now: without the member's
consent, anyone who created an organisation could add arbitrary user ids and learn
whether each exists and its display name (Q-I9). A member's `ETag` is built from the
membership `id` and `version`, so a tag for a membership that was removed and re-added
never matches the new membership. Memberships of one organisation are changed together through
`Memberships`, which enforces that rule and the last-admin rule (Q-I5). Removing a
membership deletes the row. The `identity.membership_removed` event is the audit
record.

| field | type | unit | meaning | provenance | since |
|-------|------|------|---------|------------|-------|
| `id` | `UUID` (v7) | — | Stable identity of the membership. | Platform `IdGenerator`. | Phase 2 |
| `organization_id` | `UUID` (v7) | — | The organisation. | Platform admin (Q-I9). | Phase 2 |
| `user_id` | `UUID` (v7) | — | The member. `(organization_id, user_id)` is unique. | Platform admin (Q-I9). | Phase 2 |
| `role` | `member` \| `admin` | — | The member's role in the organisation. `admin` implies `member`. | Platform admin when added; then organisation admin or platform admin. | Phase 2 |
| `version` | `int` (1 to 2 147 483 647) | count | Optimistic-concurrency version. It is 1 at creation and +1 per role change. | Computed by the aggregate. | Phase 2 |
| `created_at` | `datetime` (UTC) | — | When the user joined. | Platform `Clock`. | Phase 2 |
| `updated_at` | `datetime` (UTC) | — | When the membership last changed. | Platform `Clock`. | Phase 2 |

## Actor (value object)

Who is acting, as every authorisation policy sees it. It is built per request and never
stored.

| field | type | unit | meaning | provenance | since |
|-------|------|------|---------|------------|-------|
| `user_id` | `UUID` (v7), nullable | — | The acting user. It is null for an anonymous caller. | `User.id` of the token's user. | Phase 2 |
| `roles` | set of `Role` | — | Roles held explicitly. Policies apply the implication order. The set is empty when anonymous. | `User.roles`. | Phase 2 |
| `memberships` | set of `(UUID, OrganizationRole)` | — | The actor's organisations and their role in each, with at most one entry per organisation. The set is empty when anonymous. The caller includes only memberships of active organisations. | The user's `Membership` records. | Phase 2 |

A suspended user never gets an actor. `User.to_actor` raises `AccountSuspendedError`, a
permission-denied error.

## Policies

Every policy is a Specification over `Actor` and composes with `&`, `|` and `~`. The
default is to deny: anonymous actors hold no roles or memberships, so only
`CanReadVerifiedData` allows them.

| policy | allows |
|--------|--------|
| `IsAuthenticated` | any known (and therefore active) user |
| `HasRole(role)` | actors holding `role` directly or by implication |
| `IsAdmin` | `admin` |
| `IsModerator` | `moderator`, and `admin` by implication |
| `IsMemberOf(organization_id)` | members and admins of that organisation |
| `IsOrgAdminOf(organization_id)` | admins of that organisation |
| `IsSelf(user_id)` | that user only |
| `CanManageReferenceData` | `admin` |
| `CanModerate` | `moderator` or `admin` |
| `CanManageOrganization(organization_id)` | `admin`, or an admin of that organisation |
| `CanReadVerifiedData` | everyone, including anonymous callers (open dataset; Q10 in `docs/open-questions.md`) |

## Events

Every event carries `event_id`, `occurred_at` (UTC), `aggregate_id`, `aggregate_type`
and `version` (the aggregate's version after the change). Payloads carry ids, roles,
slugs, types and flags only. They never carry a display name, organisation name,
subject, issuer or status reason.

| event_type | aggregate_type | extra fields | emitted when |
|------------|----------------|--------------|--------------|
| `identity.user_mirrored` | `user` | `roles` | `UserFactory.mirror` records a user at first sight. |
| `identity.user_renamed` | `user` | `has_display_name` | The display name is set, changed or cleared. |
| `identity.user_role_granted` | `user` | `role` | `User.grant_role`. |
| `identity.user_role_revoked` | `user` | `role` | `User.revoke_role`. |
| `identity.user_suspended` | `user` | — | `User.suspend`. |
| `identity.user_reinstated` | `user` | — | `User.reinstate`. |
| `identity.organization_created` | `organization` | `slug`, `organization_type` | `OrganizationFactory.create`. |
| `identity.organization_renamed` | `organization` | `slug` | `Organization.rename`. |
| `identity.organization_suspended` | `organization` | `slug` | `Organization.suspend`. |
| `identity.organization_reinstated` | `organization` | `slug` | `Organization.reinstate`. |
| `identity.organization_retired` | `organization` | `slug` | `Organization.retire`. |
| `identity.membership_added` | `membership` | `organization_id`, `user_id`, `role` | `MembershipFactory.create`. |
| `identity.membership_role_changed` | `membership` | `organization_id`, `user_id`, `role`, `previous_role` | `Memberships.change_role`. |
| `identity.membership_removed` | `membership` | `organization_id`, `user_id`, `role` (the last role), with `version` as the last version | `Memberships.remove`. |

## Open questions raised by this module

| # | Question | Proposed default | Blocking |
|---|----------|------------------|----------|
| Q-I1 | Realm roles are copied from the token only at first sight (Phase 2 plan Q2). A role removed at the provider later, such as a demoted admin, stays in Yakhnama. Should roles be re-synchronised on every sign-in? | Keep first-sight mirroring for Phase 2. Demote in both places. Before production, record which roles came from the provider, so they can be re-synchronised without touching roles granted in Yakhnama. | no (security-relevant) |
| Q-I2 | Is the role implication order right? | `admin` implies `moderator`, and `org_admin` implies `org_member`. Nothing else is implied. In particular, `admin` does not imply `trusted_reporter`. | no |
| Q-I3 | What do the realm-level `org_member` and `org_admin` roles mean, given per-organisation memberships? | Markers only. Per-organisation rights come from memberships. | no |
| Q-I4 | Which organisation types exist? | `government`, `ngo`, `research`, `media`, `community`, `other`. | no |
| Q-I5 | May the only admin of an organisation be removed or demoted? | No. Another admin must be appointed first. This also applies to platform admins acting on the organisation. An organisation may start with no admin. | no |
| Q-I6 | May an issuer use plain `http`? | Only for loopback hosts, for the development realm. The platform's production settings validator requires `https` for the configured issuer. | no |
| Q-I7 | What does suspension do? | A suspended user keeps their roles and memberships but gets no actor, so every request that needs one is refused with a permission-denied error. Their record and memberships cannot be changed until they are reinstated. Their `last_seen_at` is still recorded. Suspending an organisation blocks renaming it and adding members. The application decides whether members of a suspended organisation keep their membership rights. The proposed default is no: memberships of inactive organisations are left out of the actor. | no |
| Q-I8 | Is a contact channel (email or phone) ever needed, for example for moderation follow-up? | No. None is stored. Any future need goes through the maintainer and a privacy review. | no |
| Q-I9 | Organisation membership needs the member's consent. How is a user invited to an organisation and how do they accept? | Until an invitation-and-acceptance flow exists, only platform admins may add members (`IsAdmin`). Organisation admins can still change roles and remove members. | no (security-relevant) |
